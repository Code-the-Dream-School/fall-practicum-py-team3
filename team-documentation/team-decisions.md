# Dataset and Product Decision

## Dataset

The team chose the Air Pollution API from OpenWeather.
LINK: https://openweathermap.org/api/air-pollution?collection=environmental

Why: It is free to start, covers any coordinates, returns hourly readings, and has history back to November 2020, so we have enough data to show trends.

Known limitation: OpenWeather estimates air pollution with models and satellite data. It does not report readings from ground monitoring stations, so it can miss very local pollution. We will state this on the dashboard.

Possible stretch goal: if time allows later, OpenWeather has a geocoding API that converts a city name into latitude and longitude coordinates. This would allow the dashboard to use a search-style build.

## Product Question

**Main question:** How does air quality compare across U.S. Census Divisions, and how does it change over time?

**Prioritized ideas** (we decide these now and do not add new ones in later weeks):

1. Which cities and Divisions have the best and worst air, and what health tip applies at that level according to EPA guidelines?
2. How does air quality change over time within a city (day by day, over the full history)?

## Product Question(s)


How do air quality levels and dominant pollutants compare across 33 US cities, using daily OpenWeather readings from November 2020 to today, and what health guidance applies to the AQI levels each city reached based on EPA guidelines?

## Scope

- **Geography:** United States only.
- **Cities:** 33 cities across the 9 U.S. Census Divisions (see [Cities](#cities)). No Alaska or Hawaii.
- **Time range:** November 2020 (the start of OpenWeather's history) to today, about six years, with new data added daily after that.
- **Granularity:** One Daily Reading per city per day, using the city's local date. OpenWeather returns hourly data, so a Daily Reading keeps the worst hourly AQI of that day and the mean of each pollutant. Raw data stays hourly.
- **Out of scope:** Other countries, forecasts, and station-based data sources.

## Cities

We sample by Census Division, not equally (as was https://codethedream.slack.com/archives/C0C1T7N1G6P/p1791494072511729?thread_ts=1791476248.200749&cid=C0C1T7N1G6P with a team): 2 cities per Division, plus extra cities where a Division has a large population or several climates. Each extra city covers a different climate or pollution regime (ozone-heavy, PM2.5-heavy, industrial NO₂/SO₂), not just the next-biggest city.

| Division | # | Cities |
| --- | --- | --- |
| New England | 2 | Boston, Providence |
| Middle Atlantic | 4 | New York, Philadelphia, Pittsburgh, Buffalo |
| East North Central | 4 | Chicago, Detroit, Columbus, Milwaukee |
| West North Central | 3 | Minneapolis, Kansas City, Omaha |
| South Atlantic | 5 | Washington DC, Charlotte, Atlanta, Miami, Tampa |
| East South Central | 3 | Birmingham, Memphis, Louisville |
| West South Central | 4 | Houston, Dallas, Oklahoma City, El Paso |
| Mountain | 4 | Phoenix, Salt Lake City, Denver, Boise |
| Pacific | 4 | Los Angeles, Fresno, Seattle, Portland |

Rules:

- **Weight Division figures by population.** Never take a plain mean across cities. Each city stores its metro population as of April 2020 (Census Bureau). A Division Figure is the population-weighted mean of each pollutant plus the population-weighted share of days at each AQI level. We never average the 1–5 AQI level itself.
- **Monitoring is a tie-breaker only.** OpenWeather data is modelled, so the number of EPA monitors does not change our data. When two cities fit equally, pick the one with more monitors, so a later check against AirNow/AQS stays possible.

The list lives in [`config/cities.yaml`](../config/cities.yaml) (name, state, Division, lat/lon, timezone, metro population, with data sources in its header). Changes go through a pull request.

## Data Needed

**Request:** latitude (lat), longitude (lon), start and end time (Unix timestamps).

**Response fields:**

| Field      | Meaning                                |
| ---------- | -------------------------------------- |
| dt         | Unix timestamp of the reading          |
| main.aqi   | Air quality index, 1 to 5              |
| components | CO, NO, NO2, O3, SO2, PM2.5, PM10, NH3 |

**AQI scale:** We use OpenWeather's 1 to 5 scale for the AQI levels, not the U.S. EPA scale or other country-specific scales. The health tips use EPA guidelines for each pollutant, so the tips are based on EPA guidance even though the AQI levels follow OpenWeather's scale.

| Value | Label     | 
| ----- | --------- |
| 1     | Good      |
| 2     | Fair      |
| 3     | Moderate  |
| 4     | Poor      |
| 5     | Very Poor |

The labels live in one lookup dictionary in code. The Transform step adds the label to each row.

**Health tips:** One fixed, EPA-based tip per AQI level (5 tips), stored next to the labels and added by Transform. Tips are never generated by AI, so health guidance cannot be made up.

**Pollutant units:** The API does not include units in the response. We store them as constants in code (OpenWeather lists all components in ug/m3; confirm against the docs before relying on this).

**Uniqueness:**

- API request: a response is identified by (lat, lon, start, end).
- Stored rows: one Daily Reading per city per local date. Unique key is city plus local date.

## Database Decision

Choice: Supabase, because the whole team and our cloud deployment need to share one database. Connection details are stored in environment variables (local `.env`, GitHub Environment secrets), never in committed files. All code and migrations connect with one `SUPABASE_DB_URL` (Supabase → Connect → Session pooler).

Schema changes go only through Alembic migrations in `db/migrations/`, never through the SQL Editor (see [ADR 0002](../docs/adr/0002-alembic-for-schema-migrations.md)). Code reads and writes data through SQLAlchemy Core, not supabase-py (see [ADR 0003](../docs/adr/0003-sqlalchemy-core-for-data-access.md)). Raw responses (as JSONB), Daily Readings, Insights, and pipeline run records all live in Supabase. The pipeline copies `config/cities.yaml` into a `tracked_cities` table, and a `division_figures` database view computes the population-weighted Division Figures, so the dashboard and the Insight stage use one calculation.

## ETL Process

Extract: For each city, call the API with its coordinates and a time window. Return the raw response unchanged; extract does not write anywhere.

Load raw: Save the raw response along with the request details and the time we retrieved it. Rerunning does not create duplicates.

Transform: Turn hourly raw data into one Daily Reading per city per local date (worst hourly AQI, mean pollutants). Add the city name, the AQI label and health tip from the lookup, attach units from the constants, and handle missing values (keep the row and store the missing pollutant as null).

Load: Save Daily Readings into Supabase. Use city plus local date as the unique key so rerunning the pipeline does not create duplicates.

Insights (proposed, see [ADR 0001](../docs/adr/0001-use-jev-for-insights.md)): Python computes facts per city-month, the Jev model makes typed judgments about them, and templates turn them into a short plain-language Insight.

The full history is loaded once (Backfill Run). After that, a scheduled AWS Lambda function adds each new day (Incremental Run). Locally, a Prefect flow runs the same stage functions. AWS region is not decided yet; `us-east-1` is a placeholder and should match the Supabase project's region.

## Dashboard

A Streamlit dashboard, hosted on Streamlit Community Cloud, reads Supabase with a read-only user. It lets the user pick a city or Division, shows the latest air quality label and health tip, charts pollutant levels over time, and states that the data is modelled. It redeploys when `main` changes, so `main` is protected and should also require passing checks (not set up yet).

## Template Code

The repo started from a generic practicum template. Where old files or code disagree with this document, this document wins. In particular: no Azure storage, no local gold files as a target, and no geocoding at run time (cities have fixed coordinates).
