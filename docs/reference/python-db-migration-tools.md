# Python Database Migration Tools for This Repo

> **Decision (2026-10-25):** Alembic with hand-written SQL. See [ADR 0002](../adr/0002-alembic-for-schema-migrations.md). This replaces the Supabase CLI recommendation below, because the team needs down migrations and a pip-only install. The tests behind the decision are in [Hands-on test results](#hands-on-test-results-2026-10-25).

## Context: what the repo has today

- **Target DB:** Supabase (hosted Postgres), shared by the team and the cloud deployment. "Supabase, because the whole team and our cloud deployment need to share one database." I know [9]
- **Dependencies:** `sqlalchemy>=2.0`, `alembic>=1.13`, `psycopg[binary]>=3.2`, `duckdb>=1.0` are listed. I know [1]
- **No Alembic setup exists.** No `alembic.ini` or `migrations/` directory was found. I know [1]
- **No DuckDB code exists.** The only DuckDB reference is `requirements.txt`. No `services/` file imports `duckdb`, and no docs use it for storage. I know [1]
- **Schema lives in hand-numbered or hand-named raw SQL:**
  - `db/001_pipeline_runs.sql` (`pipeline_runs`, with a CHECK on `status`). I know [2]
  - `supabase/raw_air_quality.sql` and `supabase/gold_air_quality.sql`, both `CREATE TABLE IF NOT EXISTS`. Raw has RLS enabled with no policies. I know [4][5]
  - `supabase/` has no `config.toml` and no `migrations/` folder, so the Supabase CLI is not set up. I know [4] (directory listing)
- **Run process is manual.** Docs say to paste the SQL into the Supabase SQL Editor or run `psql -f`, and "Don't edit tables by hand in the dashboard." I know [6]
- **CI does not touch the DB.** The only workflow runs `compileall services`. The pipeline-tests job is commented out. I know [10]
- **Course context:** a plain `.sql` script run in order "satisfies the deliverable." Alembic is listed as optional. I know [8]. Sprint 4 accepts "Alembic migrations or a plain `.sql` bootstrap script." I know [11]

### Drift to resolve before choosing

The design doc and the SQL files disagree:

- Design: raw responses stored as JSONB, `tracked_cities` table, `insights` table, `division_figures` view. I know [9]
- SQL: `raw_air_quality` is typed hourly columns, not JSONB. No `tracked_cities`, `insights`, or view exists yet. I know [4][9]
- Gold: the gold doc says hourly rows; the design says Daily Readings per city per local date. I know [5][7][9]

Whichever tool is picked, the first migration should follow the decided shape, not the current SQL.

## Per-tool notes

### Plain numbered SQL + small runner (current state)

- Matches what the team already does and what the course accepts. I know [8][11]
- Gap: nothing records which files ran against which database. A runner, or the Supabase migration table, is needed.
- Two conventions already exist: `db/001_...` and unnumbered `supabase/*.sql`. I know [2][4]

### Alembic

- Built around SQLAlchemy. It autogenerates by comparing metadata to the live database. I know [14]
- Autogenerate misses things by default: server defaults and CHECK constraints need explicit options. I know [14]
- RLS policies, grants, and extensions are not part of Alembic's core model. A third-party package covers policies. I know [27]
- DuckDB requires a custom Alembic impl class. I know [25]
- Already in `requirements.txt`, so no new dependency is added. I know [1]
- Using it means a second migration history next to Supabase's, unless Supabase CLI is dropped. I think, because Supabase tracks applied migrations in its own table. I know [19]

### Supabase CLI migrations

- Supabase's documented path. Files live in `supabase/migrations/<timestamp>_<name>.sql`. I know [18]
- `db push` applies only unrecorded migrations and records each one in `supabase_migrations.schema_migrations`. I know [17]
- Team rule in the docs: "never change the remote database directly." Schema changes go through files. I know [19]
- Local flow: `supabase db reset` applies all migrations to a local stack. I know [19][20]
- CI sample uses `supabase/setup-cli`, `supabase db start`, and `supabase db diff --strict-coverage`. I know [21]
- Newer option in the CLI docs: declarative schema files with `supabase db schema declarative sync`. I know [20] Not evaluated further.
- Does not cover DuckDB. I know [17]

### yoyo-migrations

- Plain SQL or Python migration files. Each migration runs in a transaction where the DB supports it. I know [23][24]
- Simple rollback model: `step(apply, rollback)`. I know [23]
- Works with Postgres via the `postgres` extra. It would bypass Supabase's own migration history. I think, because yoyo writes its own tables. I know [24]
- DuckDB support is not confirmed. I know [24]
- Smallest tool, but adds a runner the team must learn beside Supabase tooling. I think, because the Supabase docs already cover the workflow.

### Jetbase

- Exists. PyPI `jetbase` 0.18.1 (uploaded 2026-08-06, Python >=3.10). GitHub `jetbase-hq/jetbase` has a matching release. The README says one author maintains it. I know [28][29]
- Depends on `sqlalchemy>=2.0.10`, `typer`, and `rich`. Snowflake, Databricks, and ClickHouse need extras. I know [28]
- Authoring: `jetbase init` creates `migrations/` and `env.py`. `jetbase new "<name>"` creates SQL with `-- upgrade` and optional `-- rollback` sections. Versioned files are `V<timestamp>__name.sql`. Repeatable files `ROC__name.sql` re-run on change. I know [30]
- Tracking: `jetbase_migrations` (version, checksum, applied time) and `jetbase_lock`. Checksum validation and locking are listed features. I know [28][30]
- Postgres: set `sqlalchemy_url` in `env.py`. No RLS or grant handling is documented. I think RLS can be written as plain SQL, not verified. I know [30]
- DuckDB: not in the supported list. I know [28]
- CI and learning curve: `jetbase status` is documented. The apply command name was not verified. I know [30] Learning curve is low. I think, because the surface is small.
- Fit: adds a second history table beside `supabase_migrations`. Pre-1.0 and single-maintainer. I think, not recommended.

### Flask-Migrate

- Exists. PyPI 4.1.0 (uploaded 2025-01-10). GitHub `miguelgrinberg/Flask-Migrate` v4.1.0 released 10 Jan 2025. No release in about 21 months. The fetched page did not show it as archived. I know [31][32]
- Wraps Alembic (`alembic>=1.9.0`). Requires `Flask` and `Flask-SQLAlchemy`. I know [31]
- `flask db migrate -m "<msg>"` is documented. Since v4.0, `compare_type` and `render_as_batch` default to True. Commands outside the `flask` CLI need an app context. I know [33]
- Authoring, tracking, Postgres/Supabase, and DuckDB behave as Alembic does. I think, because it delegates to Alembic.
- Fit: the repo is Streamlit with no Flask app, and neither Flask package is in `requirements.txt`. Adding Flask only for migrations is not justified. If SQLAlchemy is chosen, use Alembic directly. I know [1]

### SQLAlchemy-Migrate

- Unmaintained. PyPI 0.13.0 (uploaded 2019-10-22) is the latest release. Its description calls it a fork "to get it working with SQLAlchemy 0.8." I know [34]
- The GitHub repo `openstack-archive/sqlalchemy-migrate` says it was "archived by the owner on Sep 26, 2019. It is now read-only," and points to `opendev.org/x/sqlalchemy-migrate`. I did not check the OpenDev repo. I know [35]
- Declares no Python version. Compatibility with SQLAlchemy 2.x (repo pins `>=2.0`) is not verified. I think it is unlikely.
- Authoring, tracking, up/down, Supabase, and DuckDB were not verified, since the status rules it out.
- Do not use. I think Alembic, which is the SQLAlchemy project's documented migration tool, is the current option. I know [14]

### Flyway (Redgate)

- Exists and maintained. Entry points: CLI, Java API, Maven, Gradle. The docs say it is designed for CI/CD. Current version was not verified. I know [37][38]
- The PyPI package named `flyway` is an unrelated third-party project (`hezhangjian/flyway-python`), not Redgate Flyway. I know [39]
- Runtime: the flywaydb.org docs say it "requires only Java 7+ and your JDBC driver." That is an old statement, so the current minimum Java version is not verified. I know [37]
- Editions: Community is free and open-source. Undo is marked Teams-only in the official reference. I think other features differ by edition, not verified. I know [37][38]
- Authoring: plain SQL scripts, no ORM. Versioned file naming was not verified in the fetched pages. I know [37]
- Tracking: `flyway_schema_history` by default. I know [38]
- Up/down: Undo is Teams-only. I think Community is forward-only, based on that marker.
- Postgres: Community supports PostgreSQL 10+. Older versions need Premium. Verified versions are 9.2 to 18. Supabase's Postgres version was not checked. I know [38]
- DuckDB: not verified.
- CI: designed for CI/CD pipelines. I know [37]
- Learning curve: medium, since it adds a JVM and a non-Python tool. I think.
- Fit: viable, not recommended. It would add a second history table beside `supabase_migrations`. I think.

## Non-Python alternatives

- **Flyway:** researched above. Viable, but JVM-based, and not recommended here.
- **dbmate, sqitch:** not researched. Not needed here, since the team already uses Python and Supabase. I think, because the repo has no non-Python tooling.

## Recommendation

Use **Supabase CLI migrations** as the single source of truth for Postgres schema. Put the files in `supabase/migrations/`, and move the current `db/001_pipeline_runs.sql`, `raw_air_quality.sql`, and `gold_air_quality.sql` content into timestamped migrations after the drift above is resolved.

Reasoning:

- The DB is already Supabase, and the CLI records applied migrations in the remote database. I know [17][19]
- RLS and grants are first-class concerns in Supabase, and the repo already relies on RLS. I know [4][22]
- Alembic would add a second history and needs custom work for policies and DuckDB. I know [14][25][27]
- Students get a documented team workflow with `db reset` and `db push`. I know [19]
- DuckDB is unused today. If it is adopted later, keep its schema out of the Supabase migration folder and handle it separately. I think, because the CLI does not target DuckDB. I know [17]

Keep the Python runner question open only if the team wants Python-level tests or Python-defined schema. Alembic remains the fallback if the team decides SQLAlchemy models should own the schema.

The five added candidates do not change this. Jetbase is the only new Python-native tool with recent releases, but it would still create a second history table beside Supabase's, and DuckDB is not listed. I know [28]

Add a CI step that runs `supabase db start` and applies migrations to a clean local DB. This makes "start from an empty database" checkable. I know [11][21] The sample CI step is a starting point, not a verified fit.

## Open questions

1. Which schema is the target: the design doc's JSONB and view model, or the typed hourly tables in `supabase/`? I know [4][9]
2. Is `supabase/config.toml` planned, and does every teammate have Docker for `supabase start`? I know [20]
3. How is `db/001_pipeline_runs.sql` applied today, and by whom? Not documented. I know [2][3]
4. Should `anon` and `authenticated` lose their default grants on the raw and gold tables? Supabase docs say grants and policies are separate checks, and default grants are not always automatic. The current SQL enables RLS but does not revoke grants. I know [22]
5. Does the pipeline use a secret key or service_role? Those bypass RLS when no user token is present. I know [22]
6. Is DuckDB intended for local analysis only, or as a storage target? Not stated in the repo. I know [1][9]

3. Students need a tool they can learn in one sprint, so fewer moving parts matter more than autogenerate.
